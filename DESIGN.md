# Design Notes

## Architecture

The service follows a simple layered flow:

`Route -> Controller -> Service -> Repository -> PostgreSQL`

The controller handles HTTP concerns. The search service coordinates LLM parsing and business validation. The repository owns SQL. The LLM adapter is separate from the repository so external model behavior cannot directly influence database execution.

## Request Flow

1. Express parses the JSON body.
2. Zod validates the query, pagination, and sort request.
3. The LLM receives the natural-language query and is instructed to return filter JSON only.
4. Zod validates the external response, including enum values and numeric ranges.
5. The service rejects empty or contradictory filters.
6. The repository converts known filter fields into fixed SQL conditions and `$1`, `$2` style parameters.
7. A count query and paginated data query run against PostgreSQL.
8. The response includes vehicles, pagination, and the validated filters used.

## Database Design

The `vehicles` table stores catalogue attributes in PostgreSQL-native types. Numeric values are used for price, mileage, and safety ratings. Check constraints protect enum-like values and sensible ranges even if another client writes directly to the database.

Indexes are intentionally limited to useful access paths: price, year, city/body type, and fuel/transmission. More indexes would make writes slower without helping the main access patterns.

PostgreSQL was selected because the data is structured and relational, filtering and ordering are core requirements, and SQL constraints and indexes provide strong correctness and predictable behavior.

## Why the LLM Does Not Generate SQL

SQL generated by a model would be difficult to trust, validate, and secure. The LLM is useful at understanding language, not at deciding what database commands the application may execute. It therefore returns a small, strict filter object. The application validates that object and owns the SQL template, columns, operators, and parameters.

This separates interpretation from execution and makes SQL injection prevention straightforward.

## Validation and Type Safety

TypeScript interfaces and union types describe internal data. Zod performs runtime validation because TypeScript types disappear at runtime. The code uses `unknown` for external errors and model content, then narrows values before use. Strict schemas reject unexpected keys and unsupported enum values.

## SQL Injection Prevention

Filter values are always query parameters. SQL identifiers cannot be parameters, so sort fields use a fixed map from API names to known database columns. No request value or LLM value is concatenated into a SQL identifier or SQL expression.

## Pagination and Sorting

The API uses page and limit with a maximum limit of 100. The repository calculates the offset and runs a separate count query. Sorting supports only `price`, `year`, `kmDriven`, `safetyRating`, and `createdAt`, with `asc` or `desc` direction.

## Failure Handling

Malformed JSON, unsupported filters, empty model responses, and upstream model errors become controlled application errors. Missing configuration returns `503`; a failed or malformed LLM response returns `502`; invalid client input returns `400`; a missing vehicle returns `404`. Unexpected server errors return a generic `500` without stack traces.

## Trade-offs and Scalability

Exact text matching keeps the first version easy to understand but is less forgiving than a normalized search index. A larger catalogue could add normalized lookup tables, full-text search, caching for repeated queries, read replicas, and observability. These are deliberately excluded until query volume or product requirements justify them.

The current LLM call is synchronous, so latency depends on the model. A production system could add timeouts, retry rules, rate limiting, request tracing, and a deterministic parser for common patterns. It should still preserve the structured-filter boundary.
